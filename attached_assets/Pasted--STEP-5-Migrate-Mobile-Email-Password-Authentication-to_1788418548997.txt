# STEP 5 — Migrate Mobile Email/Password Authentication to Supabase

Step 4A is complete.

The API now has the controlled temporary `dual` provider bridge:

`clerk | dual | supabase`

with `clerk` remaining the default.

Now migrate **ONLY the mobile email/password authentication flow** from Clerk to Supabase.

Do not migrate phone/SMS OTP, MFA, biometrics, admin authentication, invitations, or remove Clerk globally.

---

* Invitations

# 3. Supabase client

Use ONLY the existing mobile Supabase client created in Step 2:

`@workspace/supabase/mobile`

Do not create another Supabase client.

Use its existing persistent storage adapter.

Do not manually persist Supabase refresh tokens outside the Supabase client.

Do not put service-role credentials or secret keys in Expo.

Only:

* `EXPO_PUBLIC_SUPABASE_URL`
* `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`

may be used by mobile.

# 4. Email/password sign-in

Replace the mobile email/password Clerk sign-in implementation with Supabase Auth email/password sign-in.

The migrated flow must use the Supabase Auth session as its authentication session.

Do NOT:

* call Clerk sign-in for email/password
* call Clerk `setActive`
* use Clerk `useSessionList`
* handle Clerk `session_exists`
* manually activate a Clerk session
* maintain a second Clerk session
* copy Clerk session IDs into Supabase
* generate custom JWTs
* create custom passwords

The email/password flow must have one authentication owner:

`Supabase Auth`

---

# 5. Email/password sign-up

Replace the mobile email/password signup implementation with Supabase Auth signup.

Preserve the existing UI and user experience as much as reasonably possible.

Handle both possible Supabase outcomes:

### Session returned

If Supabase returns an authenticated session:

* keep the Supabase session
* continue through the normal authenticated application flow
* resolve the local application user through the API

### Email confirmation required

If Supabase creates the account but does not return an authenticated session because email confirmation is required:

* do NOT pretend the user is authenticated
* display/retain the appropriate verification state
* do not create a fake local session
* do not create a Clerk session

Do not add phone verification.

---

# 6. Existing verification screen

Inspect `app/verify.tsx`.

If it currently combines email verification with Clerk-specific phone/MFA behavior:

* isolate only the email/password verification portion needed by Supabase
* preserve all unmigrated Clerk phone/MFA functionality
* do not rewrite the entire verification architecture

Do not remove Clerk verification code that is still required by phone OTP/MFA.

---

# 7. API authentication

The mobile email/password flow must obtain its API bearer credential from the active Supabase session.

Use the Supabase session/access token mechanism.

Requests should conceptually become:

`Supabase session`
→ `access_token`
→ `Authorization: Bearer <access_token>`
→ API dual-provider boundary
→ Supabase verification
→ `users.auth_user_id`
→ `users.id`

Do not:

* send refresh tokens to the API
* manually decode JWTs
* manually validate JWTs on mobile
* create custom bearer tokens
* fall back to a Clerk token for a Supabase-authenticated user

---

# 8. IMPORTANT: API must remain dual during migration

Do NOT change:

`TRAVEL_LAND_API_AUTH_PROVIDER`

to `supabase`.

For development migration testing, the API may be configured explicitly as:

`TRAVEL_LAND_API_AUTH_PROVIDER=dual`

but do not modify production configuration or automatically change environment values.

The existing Clerk flows must continue to work.

This is temporary.

---

# 9. Local user mapping

The migrated Supabase user must resolve through:

`Supabase auth.users.id`
→ `users.auth_user_id`
→ `users.id`

The local:

`users.id`

remains the application identity.

Never replace it with the Supabase UUID.

Do NOT use:

`Supabase email → users.email`

as a fallback.

Do NOT automatically attach a Supabase user to a local account by email.

Do NOT create an `auth_user_id` mapping from the mobile client.

Do NOT create fake mappings.

---

# 10. Handle missing mapping safely

There are currently no approved `auth_user_id` mappings.

Therefore the implementation must explicitly handle:

`Supabase authentication succeeds`
but
`local users.auth_user_id mapping does not exist`

The API will return 401.

The mobile app must:

* not enter protected application state as though the user is fully provisioned
* not assign ownership
* not create a local user automatically
* not match by email
* show a safe application/authentication error state
* avoid an infinite login loop

Do not work around the 401.

If the existing application requires local-user provisioning for newly created accounts, STOP and report that dependency rather than inventing provisioning logic.

---

# 11. Auth state architecture

Do not blindly replace every occurrence of:

`isSignedIn`

or

`userId`

with Supabase equivalents.

Some of those values are currently shared with:

* phone OTP
* MFA
* biometric security
* role loading
* app state
* navigation

Create or use a provider-neutral mobile authentication abstraction if necessary.

The abstraction should allow:

`Clerk` for unmigrated flows

and

`Supabase` for migrated email/password.

However, email/password itself must not create both sessions.

1. Supabase session exists
2. API authentication succeeds
3. local user mapping resolves
4. existing role/account checks succeed

* RoleContext

# 15. Logout

For the migrated email/password path:

Use Supabase Auth sign-out.

Do not call Clerk sign-out as part of the normal Supabase email/password logout.

However, preserve Clerk logout behavior for users currently authenticated through the unmigrated Clerk flows.

Do not globally replace logout until all providers have been migrated.

---

# 16. Session restoration

On app restart:

Supabase should restore its persisted session through the existing mobile Supabase client.

Do not recreate sessions manually.

Do not use Clerk session restoration for a Supabase email/password session.

Do not automatically sign the user into Clerk based on a Supabase session.

If the Supabase session is expired and cannot be refreshed:

* clear/handle the Supabase authentication state normally
* do not silently fall back to Clerk

---
