# STEP 4 — Migrate Mobile Email/Password Authentication from Clerk to Supabase

Step 3 API authentication boundary is complete and has passed its focused security tests. Proceed with **Step 4 only**.

## Objective

Migrate the existing **mobile email/password authentication flow** from Clerk to Supabase Auth.

Supabase must become the authentication provider for the migrated email/password flow, while the rest of the application remains unchanged.

This is a controlled migration. **Do not remove Clerk globally yet.**

---

## IMPORTANT SCOPE — DO ONLY THIS STEP

### In scope

* Mobile email/password sign-in
* Mobile email/password sign-up
* Supabase session persistence/restoration for these flows
* Mapping an authenticated Supabase user to the existing local `users.id`
* API calls using the Supabase access token
* Existing login/signup success navigation
* Existing authenticated app behavior after login

### Explicitly OUT OF SCOPE

Do NOT migrate or modify:

* Phone/SMS OTP
* Phone verification
* MFA
* Biometric/device unlock implementation
* Admin authentication
* Invitations
* Password reset unless it is inseparable from the existing email/password implementation
* OpenAPI
* Generated API clients
* Database ownership relationships
* Bookings
* Favorites
* Reviews
* Wallet
* Roles/permissions
* Clerk database columns
* `users.clerk_user_id`
* Clerk package removal
* Global Clerk removal
* Supabase API provider switching
* Production configuration

Do not "clean up" unrelated Clerk code.

---

# 1. Inspect the current mobile email/password flow first

Before editing, inspect:

* `artifacts/travel-land-app/app/_layout.tsx`
* `artifacts/travel-land-app/app/login.tsx`
* `artifacts/travel-land-app/app/verify.tsx`
* `features/auth/PasswordResetFlow.tsx`
* `context/AuthSecurityContext.tsx`
* `context/AppStateContext.tsx`
* `context/RoleContext.tsx`
* existing API/auth hooks and utilities
* current Clerk token getter
* current authenticated navigation logic
* existing email/password tests

Identify exactly where the current Clerk email/password flow:

1. starts sign-in
2. starts sign-up
3. verifies email
4. creates/finalizes a session
5. activates/restores a session
6. obtains an API bearer token
7. determines whether the user is signed in
8. navigates into the authenticated application

Do not change anything until this flow is understood.

---

# 2. Use the existing Supabase mobile client

Use the Supabase mobile client created in Step 2.

Do NOT create another Supabase client.

Use:

`@workspace/supabase/mobile`

and its existing injected SecureStore-compatible storage adapter.

Supabase mobile session persistence must remain enabled.

Do not put:

* service-role key
* secret key
* server credentials

inside Expo/mobile code.

Only the publishable Supabase client configuration may be used by the mobile app.

---

# 3. Email/password SIGN UP

Replace the Clerk email/password signup operation with the equivalent Supabase Auth operation.

Use Supabase Auth's normal email/password signup API.

Do not implement:

* custom password hashing
* custom JWTs
* custom session tokens
* custom authentication endpoints
* custom OTP/JWT generation

Preserve the existing UI and UX as much as possible.

After successful Supabase signup:

* use the Supabase-authenticated user/session state
* do not manufacture a local application user
* do not match users by email
* do not silently create a `users` row in this step unless the existing application already has an explicitly required provisioning path that must be preserved

If email confirmation is required by the Supabase project configuration, preserve the correct verification state and do not pretend the user is fully authenticated when Supabase has not established an authenticated session.

Do not implement phone verification as part of this step.

---

# 4. Email/password SIGN IN

Replace the Clerk email/password sign-in operation with Supabase Auth email/password sign-in.

Use the standard Supabase Auth password sign-in method.

The resulting Supabase session must become the authoritative client authentication session for this migrated flow.

Do NOT:

* call Clerk sign-in
* activate a Clerk session
* reuse `useSessionList()`
* handle Clerk `session_exists`
* manually copy Clerk session IDs
* maintain two competing authenticated sessions

The migrated email/password flow should have one session owner:

`Supabase Auth`

---

# 5. Existing local user mapping

After Supabase authentication succeeds, the application still needs its existing local user identity.

Use the identity model created in Step 2/3:

`Supabase auth.users.id`
↓
`users.auth_user_id`
↓
`users.id`

The Supabase user UUID must NOT replace the existing local `users.id`.

Do not change ownership IDs for:

* bookings
* favorites
* reviews
* wallet
* enquiries
* properties
* other application records

Do not use email matching as a fallback.

Do not automatically create or migrate a local user based only on email.

For this step, if the authenticated Supabase user has no corresponding `users.auth_user_id` mapping, fail safely and provide the existing appropriate authentication/application error state rather than assigning ownership incorrectly.

If the existing application has a clearly documented local-user provisioning requirement that conflicts with this, STOP and report it instead of inventing a new provisioning rule.

---

# 6. API bearer token

Update the migrated mobile email/password flow so authenticated API requests use the Supabase access token.

The API request path should become conceptually:

`Supabase Auth session`
↓
`Supabase access token`
↓
`Authorization: Bearer <token>`
↓
`API authentication boundary`
↓
`users.auth_user_id`
↓
`users.id`
↓
existing authorization/ownership

Do not manually decode the token on mobile.

Do not create a custom authorization header format.

Do not send Supabase refresh tokens to the API.

Only the access token should be used as the API bearer credential.

---

# 7. API provider switching — DO NOT DO IT

Do NOT change:

`TRAVEL_LAND_API_AUTH_PROVIDER`

Do NOT switch the API to Supabase yet.

Keep:

`TRAVEL_LAND_API_AUTH_PROVIDER=clerk`

This is important because Step 3 deliberately created an opt-in API boundary.

Since real Supabase configuration and `auth_user_id` mappings are not yet available, do not activate Supabase API authentication globally.

If the mobile app is changed to send Supabase tokens while the API remains Clerk-only, do NOT invent a compatibility workaround or modify the API to accept both providers.

Instead, identify and report this transition dependency clearly.

If necessary, implement the client-side auth abstraction so the actual provider switch can happen in the next controlled step, but do not weaken Step 3's fail-closed provider selection.

---

# 8. Auth state and navigation

Replace only the email/password-related Clerk state dependencies.

Preserve:

* existing loading states
* existing login UI
* existing signup UI
* existing error handling where applicable
* existing authenticated navigation
* existing unauthenticated navigation
* existing role loading
* existing biometric gate
* existing app startup behavior

Do not allow the app to navigate into protected screens merely because a Supabase user object exists locally if the application requires an authenticated API/local-user mapping.

The authenticated state should ultimately be based on a valid persisted Supabase session plus the application's existing authorization requirements.

---

# 9. Biometric behavior

Do NOT migrate or rewrite biometric logic in Step 4.

Biometric/device unlock remains a local security gate layered over authentication.

Preserve the existing `AuthSecurityContext` behavior.

Do not store passwords in biometric storage.

Do not store Supabase refresh tokens manually in the biometric storage.

Let the existing Supabase mobile client own session persistence.

---

# 10. Clerk must remain available

Clerk remains installed and functional for the flows not yet migrated.

Do NOT remove:

* `@clerk/expo`
* Clerk provider setup
* Clerk-specific phone/MFA code
* Clerk admin code
* Clerk API code
* Clerk invitation code

unless a file contains only dead email/password code and removing it is absolutely necessary for the migrated flow.

If a shared file contains both migrated and unmigrated Clerk functionality, preserve the unmigrated functionality.

# 11. Tests

Add/update focused tests for the migrated mobile email/password flow.

At minimum test:

### Sign-in

1. Valid email/password → Supabase sign-in succeeds.
2. Invalid credentials → safe error state.
3. Supabase session is persisted.
4. Existing authenticated navigation still works.
5. API token retrieval comes from Supabase, not Clerk.

### Sign-up

6. Valid email/password → Supabase signup is invoked.
7. Existing signup UI state is preserved.
8. Email-confirmation-required state is handled correctly.
9. No Clerk session is created.

### Identity mapping

10. Supabase `user.id` maps through `users.auth_user_id`.
11. Existing local `users.id` remains the application identity.
12. Unmapped Supabase user does not get silently matched by email.
13. Unmapped Supabase user does not get ownership assigned to another local user.

### Regression

14. Existing biometric/security tests continue to pass.
15. Existing authenticated navigation tests continue to pass.
16. Existing Clerk phone/MFA tests remain unchanged.
17. Existing admin authentication tests remain unchanged.

Add a regression test proving the migrated email/password path does not call Clerk authentication APIs.
