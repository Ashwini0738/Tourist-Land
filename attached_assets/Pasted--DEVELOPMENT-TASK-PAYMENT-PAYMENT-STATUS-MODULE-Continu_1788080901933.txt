# 2. PAYMENT PROVIDER

Inspect the existing project and determine whether a payment provider is already configured.

If one exists:

Reuse it.

If none exists:

Choose a production-ready provider appropriate for the application's target market.

Keep the provider integration behind a clean payment service abstraction.

The application should be able to replace the provider later without rewriting the Booking module.

Do NOT put secret API keys in:

* React Native code
* Expo public environment variables
* Git
* GitHub
* client-side source

Server-side secrets only.

---

# 3. ENVIRONMENT VARIABLES

Use environment variables for payment configuration.

Separate:

### Server secrets

Examples:

* PAYMENT_SECRET_KEY
* PAYMENT_WEBHOOK_SECRET

### Client-safe configuration

Only expose values that are explicitly safe for the client.

Do not expose private payment credentials.

Create/update the project's environment documentation.

---

# 4. PAYMENT ORDER / INTENT

Before opening the payment UI, create a server-side payment order/intent.

Potential endpoint:

POST /api/v1/payments/create

The server should:

1. Authenticate the user.
2. Verify booking ownership.
3. Verify booking is payable.
4. Revalidate booking status.
5. Revalidate payment status.
6. Verify the authoritative booking total.
7. Create a payment order/intent with the gateway.
8. Return only the client-safe payment information.

Never allow the client to choose an arbitrary payment amount.

---

# 5. PAYMENT AMOUNT

The payment amount must come from the server-side booking total.

Do NOT trust:

* amount from React Native
* amount from route parameters
* amount from local state
* amount from AsyncStorage

The server must determine the amount.

---

# 6. PAYMENT STATUS

Maintain payment status separately from booking status.

Suggested payment states:

* unpaid
* pending
* processing
* paid
* failed
* cancelled
* refunded
* partially_refunded

Do not mark payment as "paid" based only on a frontend callback.

---

# 7. PAYMENT VERIFICATION

This is critical.

After the user completes payment:

The server must verify the payment with the payment provider.

Possible flow:

Client
→ Payment Gateway
→ Payment Result
→ Server Verification
→ Webhook/Provider Confirmation
→ Update Payment
→ Update Booking

The frontend callback must NOT be considered authoritative.

---

# 8. WEBHOOK

Implement a secure payment webhook endpoint.

Potential endpoint:

POST /api/v1/payments/webhook

The webhook must:

* Verify provider signature
* Reject invalid signatures
* Process valid payment events
* Be idempotent
* Update payment status
* Update booking status appropriately

Never trust webhook data without signature verification.

---

# 9. IDEMPOTENCY

Prevent duplicate payments and duplicate booking confirmation.

Handle:

* User double taps
* Network retries
* App restart
* Payment callback retry
* Webhook retry
* Gateway retry

The same payment event must not create duplicate transactions.
