## STEP 6A — REAL DEVICE END-TO-END VALIDATION ONLY

Step 6A implementation and automated validation are complete.

Do NOT modify application code unless the real-device test exposes a confirmed defect.

Do NOT start Step 7.

### TEST OBJECTIVE

Verify the complete existing-user migration flow on a real Android device:

**Existing Clerk account**
→ **Account Security**
→ **Add email sign-in**
→ **Supabase email/password**
→ **server-side identity linking**
→ **Supabase session restored**
→ **existing local account remains the same**

### TEST 1 — BEFORE MIGRATION

Using an existing test account that already has a valid Clerk identity:

1. Sign in normally.
2. Confirm the correct user profile is displayed.
3. Record/verify the user's existing application data:

   * profile
   * bookings
   * favorites
   * reviews/enquiries if applicable
   * wallet if applicable
4. Confirm the user remains authenticated through the existing Clerk flow.

Do NOT use a production account.

### TEST 2 — START MIGRATION

From Account Security:

1. Select **Add email sign-in**.
2. Enter the test email/password.
3. Complete the Supabase email verification flow if required.
4. Complete the migration.

Verify:

* No email-only identity matching is occurring.
* No user ID is manually entered.
* No provider ID is manually entered.
* The migration attempt completes successfully.
* No duplicate local user is created.

### TEST 3 — VERIFY IDENTITY MAPPING

After successful migration, verify server-side that:

`users.id`

is exactly the same local user ID as before migration.

Verify:

`users.clerk_user_id`

is unchanged.

Verify:

`users.auth_user_id`

now contains the verified Supabase `auth.users.id`.

Verify:

* role unchanged
* ownership unchanged
* bookings unchanged
* favorites unchanged
* reviews/enquiries unchanged
* wallet unchanged

Do NOT expose tokens or credentials in logs.

### TEST 4 — SESSION HANDOFF

After linking:

1. Confirm the mobile app obtains the Supabase session.
2. Confirm API requests can authenticate with the Supabase token.
3. Confirm `/v1/me` resolves to the same local user.
4. Confirm the app does NOT create a second local user.
5. Confirm the app does NOT show the unmapped-account state after successful linking.

### TEST 5 — APP RESTART

Completely close the app.

Reopen it.

Verify:

* Supabase session is restored.
* Correct user remains signed in.
* Profile is correct.
* Existing application data remains available.
* No Clerk/Supabase session conflict occurs.

### TEST 6 — LOGOUT / LOGIN

Log out.

Then log back in using the new Supabase email/password flow.

Verify:

* Login succeeds.
* Correct local user is resolved.
* Existing data remains attached to the same `users.id`.

### TEST 7 — NEGATIVE SECURITY CHECK

Do NOT use real credentials from another person.

Using controlled test identities, verify that:

* a Supabase identity already linked to another local user cannot be linked again
* an existing local user already linked to a different Supabase identity cannot be overwritten
* an expired migration attempt cannot be completed
* a migration attempt cannot be replayed

Do not weaken security checks to make a test pass.
