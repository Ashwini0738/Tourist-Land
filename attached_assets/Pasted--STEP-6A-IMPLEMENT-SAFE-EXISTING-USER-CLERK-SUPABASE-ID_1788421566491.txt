# PRIMARY GOAL

Allow an EXISTING authenticated Clerk user to securely link their own Supabase identity.

The server must independently verify BOTH identities.

The final mapping must be:

`Supabase auth.users.id`
→ `users.auth_user_id`
→ existing `users.id`

while preserving:

* existing `users.id`
* `users.clerk_user_id`
* role
* ownership
* bookings
* favorites
* reviews
* wallet
* invitations
* all existing application relationships

Do NOT create a new local `users` record during this step.

---

# SECURITY REQUIREMENT — CRITICAL

Never accept arbitrary identity IDs from the client and trust them.

The client must NOT be able to say:

`clerk_user_id = X`

and:

`supabase_user_id = Y`

and ask the server to link them.

The server must derive both identities from independently verified credentials.

Do NOT use:

* email equality
* email lookup
* biometric state
* local storage values
* client-supplied Clerk user ID
* client-supplied Supabase user ID
* recovery-session state
* access-token contents without verification
* refresh-token contents
* admin-entered identity IDs

as proof of ownership.

---

# REQUIRED FLOW

Implement a user-authenticated migration flow approximately as follows:

### Step 1 — Existing Clerk authentication

The existing user authenticates through the current Clerk flow.

The server independently verifies the Clerk session/token and derives:

`verified Clerk subject`

Then resolve:

`users.clerk_user_id = verified Clerk subject`

This identifies the existing local user.

Do NOT identify the local user by email.

---

### Step 2 — Supabase authentication

The same user authenticates with Supabase email/password.

The server independently verifies the Supabase access token using the existing Supabase JWT verification boundary.

Derive:

`verified Supabase auth.users.id`

Do NOT accept the Supabase user ID as a request-body parameter.

---

### Step 3 — Verify both identities

The server must establish:

`verified Clerk identity`
+
`verified Supabase identity`

before creating the mapping.

The identities must belong to the same authenticated migration attempt.

Do not allow a client to mix credentials from unrelated accounts.

---

# MIGRATION ATTEMPT / REPLAY PROTECTION

Implement a short-lived, one-time migration attempt mechanism if required by the existing architecture.

A suitable design may use a dedicated table such as:

`identity_link_attempts`

but first inspect the existing schema and architecture.

If a migration-attempt table is needed, it should contain only the minimum metadata required for:

* one-time use
* expiration
* migration attempt ID
* existing local user ID
* verified Clerk subject
* verified Supabase subject, if appropriate
* status
* created/used timestamps
* audit information

NEVER store:

* access tokens
* refresh tokens
* passwords
* OTP codes
* session secrets

Use cryptographically secure random identifiers/nonces.

Prevent:

* replay
* reuse
* cross-user substitution
* expired attempts
* concurrent conflicting mappings

# DATABASE TRANSACTION

The final mapping must be transactional.

Before writing:

1. Resolve the existing local user from the VERIFIED Clerk identity.
2. Resolve the VERIFIED Supabase identity.
3. Confirm the Supabase identity is not already mapped to another local user.
4. Confirm the existing local user does not already have a conflicting `auth_user_id`.
5. Perform the mapping atomically.

Set only:

`users.auth_user_id = verified Supabase subject`

Do NOT modify:

`users.id`

Do NOT modify:

`users.clerk_user_id`

Do NOT modify role or ownership.

If any constraint/conflict occurs, roll back the entire operation.

# EXISTING USER ALREADY MAPPED

Handle these cases explicitly.

### Case A

The local user already has:

`users.auth_user_id = this Supabase subject`

Return a safe idempotent success/already-linked result.

### Case B

The local user has a different `auth_user_id`

Reject the migration as a conflict.

Do not overwrite it automatically.

### Case C

The Supabase subject is already mapped to another local user

Reject the migration.

Do not merge users.

Do not reassign the identity.

### Case D

The Clerk identity does not resolve to a local user

Reject safely.

Do not create a new local user in Step 6A.

### Case E

The Supabase identity is valid but unmapped

Allow linking only after the verified two-provider migration flow succeeds.
