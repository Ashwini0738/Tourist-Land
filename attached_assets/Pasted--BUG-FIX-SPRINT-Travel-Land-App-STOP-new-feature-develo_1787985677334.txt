# BUG 1 — Replit Preview Blinking / Infinite Loading After "Skip for now"

## Current behavior

In the Replit browser/mobile-web preview:

1. Application loads.
2. User reaches the biometric/device security screen.
3. User clicks "Skip for now".
4. Screen starts blinking/re-rendering.
5. Loading continues indefinitely.
6. Browser becomes unresponsive and shows "Wait or close page".

## Expected behavior

When the user selects:

"Skip for now"

the application should:

1. Stop the biometric setup flow.
2. Persist the appropriate onboarding/setup state.
3. Continue to the correct next screen.
4. Stop all loading indicators.
5. Stop any authentication/setup retry loop.
6. Never continuously remount the screen.
7. Never continuously trigger Clerk/session initialization.
8. Never continuously trigger biometric detection.

If the user is not authenticated yet, navigate to the appropriate authentication screen.

If the user is already authenticated, continue to the appropriate authenticated screen.

## Investigation

Inspect:

* Authentication state
* Clerk session initialization
* Biometric initialization
* PIN initialization
* "Skip for now" state
* Expo Router redirects
* Protected route guards
* useEffect dependencies
* navigation redirects
* loading state management
* AsyncStorage/local storage usage
* React Query initialization
* Any polling/retry loops

Look specifically for:

* useEffect causing repeated navigation
* state updates inside effects causing infinite renders
* authentication redirects fighting each other
* loading state never becoming false
* biometric initialization being triggered repeatedly
* route guard redirect loops
* session initialization running multiple times
* component remount loops

Add appropriate guards so initialization happens only once per intended lifecycle.

Do NOT simply add arbitrary delays or setTimeout hacks.

Fix the root cause.

# BUG 3 — Biometric → Email → OTP Happens on Every Expo Go Scan

## Current behavior

Every time the user scans the Expo QR code:

1. Biometric prompt appears.
2. After biometric authentication, application moves to email login.
3. User signs in with email/password.
4. Clerk asks for an email OTP verification.
5. User must complete OTP verification again.
6. This repeats on subsequent scans.

This creates the impression that the application is creating a new authentication flow every time Expo Go starts.

## Expected behavior

Separate these concepts:

### Account authentication

Clerk should authenticate the user and establish a persistent session.

### Biometric unlock

Biometric authentication should unlock an existing authenticated session/credential on the device.

Biometrics must NOT:

* create a new Clerk account
* replace Clerk authentication
* automatically restart email authentication
* force email OTP every time the app is opened

After the user has successfully authenticated once and enrolled biometrics:

Next app launch should ideally be:

App opens
→ existing secure credential/session detected
→ biometric prompt
→ biometric succeeds
→ user enters application

If the Clerk session is still valid, do NOT show email login again.

If the Clerk session has genuinely expired, then show the appropriate Clerk authentication flow.

# OTP Investigation

The email OTP should only appear when Clerk legitimately requires verification.

Investigate why verification is being requested repeatedly.

Check whether:

* A new sign-in attempt is created on every app start.
* The app calls signIn repeatedly.
* The verification state is recreated after biometric authentication.
* Session restoration is bypassed.
* Email verification is incorrectly triggered even when the account/session is already verified.

Do not bypass Clerk security or disable legitimate MFA/verification requirements.

The goal is to preserve security while avoiding unnecessary repeated authentication.

# Biometric Flow

The intended architecture should be approximately:

FIRST LOGIN:

Clerk Login
→ Email verification/MFA if required
→ Clerk session established
→ User creates PIN
→ User enables biometrics
→ Secure credential/session state stored
→ Home

RETURNING USER:

App Start
→ Restore Clerk session
→ If valid session exists
→ Biometric unlock if enabled
→ Home

If biometric is unavailable:

App Start
→ Restore Clerk session
→ PIN fallback
→ Home

If Clerk session has expired:

App Start
→ Clerk authentication
→ Required verification
→ New session
→ Optional biometric enrollment

Do not run the full account authentication flow on every launch.

* Store passwords in AsyncStorage.

* Hardcode OTPs.
* Create fake authentication success.
* Bypass MFA.
* Store sensitive credentials insecurely.
* Automatically trust an unauthenticated client.

Maintain the existing server-side PIN hashing and lockout behavior.
