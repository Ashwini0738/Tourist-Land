### Objective

Perform a **read-only security and architecture analysis** to determine exactly how an existing application user can safely move from Clerk authentication to Supabase authentication without changing the existing application identity.

The required identity model remains:

`Supabase auth.users.id`
→ `users.auth_user_id`
→ existing `users.id`

The existing `users.id` remains the permanent application/ownership identity.

Inspect the current implementation for:

* Clerk signup
* Clerk email/password authentication
* Clerk phone authentication
* Clerk MFA
* Clerk user provisioning
* local `users` creation
* `users.clerk_user_id`
* `users.auth_user_id`

* `/v1/me` or equivalent current-user resolution
* profile creation/update
* application ownership
* bookings
* favorites
* reviews
* wallet
* enquiries
* any other records referencing `users.id`

Determine exactly how a user currently becomes an application user.

## 2. Determine the two migration cases

Analyze separately:

### CASE A — Brand-new user

Determine whether the current application allows:

`Supabase signup`
→ verified Supabase identity
→ create local `users` record
→ populate `auth_user_id`

If yes, document the exact existing registration rules that must be preserved.

If invitations/approval are required, document that instead.

Do not invent new business rules.

### CASE B — Existing user

Determine whether the current architecture provides a trustworthy way to prove that:

`Existing Clerk user`
and
`Supabase auth user`

belong to the same person.

Investigate whether this can be safely established through:

* simultaneous authenticated sessions
* an authenticated migration session
* a server-side migration transaction
* an existing trusted account-management flow
* another existing mechanism already present in the application

Do NOT assume email equality proves identity.

Do NOT create an admin endpoint that accepts arbitrary Clerk ID + Supabase ID.

Do NOT create a client-controlled mapping mechanism.

---

## 3. Evaluate possible safe migration designs

For existing users, analyze at least these possible approaches:

### Option A — User-authenticated migration

Existing authenticated user proves control of the existing account and separately authenticates to Supabase.

Evaluate whether the current application can safely perform:

`trusted existing identity`
+
`verified Supabase identity`
→ server-side mapping

### Option B — Admin-controlled migration

Evaluate whether an administrator could safely approve a mapping.

If this is considered, the server must have a trustworthy verification process and must NOT simply trust two IDs submitted by the admin UI.

Explain exactly what proof/confirmation would be required.

### Option C — Explicit account re-authentication

Evaluate whether the user can authenticate through both systems during migration and whether the server can securely correlate those authenticated sessions.

### Option D — New-account provisioning

Evaluate whether it is safer for users without an existing local account to create a new local user through Supabase while preserving all existing authorization rules.

---

## 4. Security requirements

The final design MUST guarantee:

* No email-only identity matching.
* No client-supplied identity pair trusted as proof.
* No arbitrary `users.id` supplied by client.
* No arbitrary `auth_user_id` supplied by client.
* No change to existing `users.id`.
* No reassignment of bookings.
* No reassignment of favorites.
* No reassignment of reviews.
* No reassignment of wallet records.
* No reassignment of enquiries.
* No role escalation.
* No automatic Clerk identity reassignment.
* No automatic ownership transfer.
* Existing `users.clerk_user_id` remains available during migration/rollback.
* Supabase JWT is independently verified.
* Clerk identity is independently verified when used.
* Server derives identities from verified authentication contexts.
* Mapping is transactional.
* Mapping is one-to-one.
* Conflicting mappings fail closed.
* Failed migration leaves the database unchanged.

## 6. Migration state model

Design a clear state model for users during migration.

For example, determine whether the system needs to distinguish:

* Clerk-only user
* Supabase-only user
* dual-linked user
* unmapped Supabase user
* migration-pending user
* migration-complete user

Use the existing schema where possible.

Do not add states merely for theoretical reasons.

## 8. Mobile behavior

Determine how the mobile application should behave when:

1. Existing Clerk user has not migrated.
2. User signs in through Supabase but is not mapped.
3. User successfully completes migration.
4. User closes the app during migration.
5. Migration partially fails.
6. User signs out.
7. Biometric unlock is enabled.

Biometric must remain a local device-unlock layer and must NOT be treated as proof of server identity migration.

Do not change mobile code in this step.

---

## 9. Rollback strategy

Design how a user can safely remain usable during the migration period.

Determine whether:

* Clerk remains available for rollback
* Supabase remains available after successful linking
* both identities can temporarily coexist
* `users.clerk_user_id` should remain untouched
* an already-linked Supabase identity can ever be unlinked

Do not implement unlinking unless there is a clear security-safe reason.
