# ROLE-BASED AUTHENTICATION — ADMIN, VENDOR AND USER

Continue development of the existing **Travel & Land** application.

The existing authentication system is COMPLETE and must remain intact:

* Clerk authentication
* Email/password
* Email verification / OTP / MFA when required
* Native fingerprint / Face ID / device authentication
* Returning-user authentication
* Secure session handling
* Protected routes

Do NOT replace Clerk.

Do NOT create separate authentication systems for Admin, Vendor and User.

Implement **one authentication system with three roles and role-based authorization**.

---

# 1. THREE USER ROLES

The application must support exactly these primary roles:

### USER

Normal traveller/customer.

### VENDOR

Business/property/service provider.

### ADMIN

Platform administrator.

Use stable role identifiers:

* user
* vendor
* admin

Do not use display names as authorization values.

---

# 2. USER ROLE

A normal USER should have access to:

* Home
* Explore
* Destinations
* Places
* Events
* Hotels
* Hotel details
* Maps
* Bookings
* My Bookings
* Favorites
* Reviews
* Wallet
* Land/property discovery
* Property details
* Land enquiries
* Profile
* Notifications

A USER must NOT have access to:

* Admin dashboard
* User management
* Vendor management
* Platform settings
* Vendor inventory management
* Other vendors' private data
* Admin APIs

---

# 3. VENDOR ROLE

A VENDOR represents a business/property/service provider.

Vendors should eventually be able to manage:

### Vendor dashboard

* Dashboard
* Profile
* Business information
* Listings
* Hotels
* Rooms
* Room pricing
* Availability
* Properties
* Property details
* Images
* Bookings related to their listings
* Customer enquiries
* Reviews
* Notifications

Vendor access must be restricted to their own data.

For example:

Vendor A must NOT be able to:

* Edit Vendor B's hotel
* View Vendor B's private bookings
* Modify Vendor B's property
* Delete another vendor's listing
* Access admin-only APIs

Enforce this on the SERVER.

Do not rely only on hiding UI buttons.

---

The role must be available to both:

* Client UI

**The server must be the ultimate authority for authorization.**

Do not trust a role value supplied by the client request body.

# 8. ROLE ASSIGNMENT

Do NOT create public signup screens that allow users to simply select:

"Admin"

and gain administrator access.

Admin role assignment must be controlled securely.

Vendor role assignment should also be controlled appropriately.

Recommended flow:

### Normal signup

User creates Clerk account
→ default role = USER

### Vendor onboarding

User requests/becomes Vendor
→ Vendor profile created
→ status = pending
→ Admin approves
→ role becomes VENDOR / vendor access activated

### Admin

Admin role is assigned only through a secure administrative mechanism.

Never allow a client-side request to promote itself to admin.

---

# 9. AUTHORIZATION MIDDLEWARE

Implement reusable server-side authorization.

Examples:

requireAuthenticatedUser()

requireRole("user")

requireRole("vendor")

requireRole("admin")

requireAnyRole(["admin", "vendor"])

Use these protections on API endpoints.

Example:

GET /api/v1/admin/users
→ ADMIN only

POST /api/v1/admin/vendors/approve
→ ADMIN only

POST /api/v1/vendor/hotels
→ VENDOR only

PUT /api/v1/vendor/hotels/:id
→ VENDOR + ownership check

GET /api/v1/bookings
→ AUTHENTICATED USER

---

# 10. OWNERSHIP AUTHORIZATION

For vendor resources, authorization must check ownership.

Example:

Vendor A requests:

PUT /api/v1/vendor/hotels/123

The server must verify:

hotel.vendor_id === authenticated_vendor.id

If not:

Return HTTP 403 Forbidden.

Do not rely on the frontend hiding the hotel.

Apply the same principle to:

* Hotels
* Rooms
* Properties
* Availability
* Vendor bookings
* Enquiries
* Vendor-specific reviews where applicable
