# PART A — NOTIFICATIONS

## 1. NOTIFICATIONS SCREEN

Create a mobile-first Notifications screen.

Display:

* Notification title
* Short message
* Date/time
* Read/unread state
* Notification type
* Optional related image/icon

Group notifications where useful:

* Today
* Yesterday
* Earlier

Do not display fake notifications.

---

# 2. NOTIFICATION TYPES

Prepare support for:

### Booking

* Booking created
* Payment successful
* Payment failed
* Booking confirmed
* Booking cancelled
* Booking reminder

### Payment

* Payment pending
* Payment successful
* Payment failed
* Refund processed

### Land

* Land enquiry received
* Enquiry status updated
* Vendor/admin response

### General

* New destination
* Event update
* Offer/promotion

Only create notification types for events that actually exist.

Do not generate sample notifications just to populate the screen.

---

# 3. NOTIFICATION DATABASE

Inspect the existing schema first.

If required, create:

### Notification

* id
* user_id
* type
* title
* message
* related_type
* related_id
* read_at
* created_at

Notifications must belong to a specific authenticated user.

GET /api/v1/notifications

Reuse existing API conventions.

Update:

* OpenAPI
* Generated TypeScript client
* React Query hooks
* Zod schemas

---

# 5. READ / UNREAD

Implement:

* Mark notification as read
* Mark all as read
* Unread count

Unread notifications should have clear visual distinction.

The server is authoritative.

Do not store read/unread state only in AsyncStorage.

---

# 6. NOTIFICATION NAVIGATION

When a notification relates to an entity:

Booking notification
→ Booking Details

Payment notification
→ Booking/Payment Details

Land notification
→ Property/Enquiry Details

Destination notification
→ Destination Details

Do not create dead-end notifications.

If related content no longer exists:

Show the notification but handle the missing destination gracefully.

---

# 7. PUSH NOTIFICATION FOUNDATION

Prepare the application for push notifications.

Implement:

* Device push token registration
* User association
* Token update
* Token removal on logout
* Permission handling

Use Expo-compatible push notification architecture where appropriate.

Do not expose push credentials.

Do not send fake push notifications.

---

# 8. PUSH PERMISSION UX

Do not request notification permission immediately on app launch without context.

Use a sensible permission flow.

If permission is denied:

The in-app notification center must still work.

# PART B — FAVORITES

## 9. ACCOUNT-SYNCHRONIZED FAVORITES

The existing app stores favorites locally.

Replace or extend this with server-side synchronization.

Favorites should work across:

* Android
* iOS
* Mobile web
* Multiple devices
* Sessions

The authenticated user's server-side favorites are authoritative.

---

# 10. FAVORITE TYPES

Support favorites for:

* Destinations
* Hotels
* Properties/Land listings
* Places where supported

Do not create separate unrelated favorite systems for each entity unless necessary.

Use a reusable favorite model where practical.

---

# 11. FAVORITE MODEL

Possible structure:

### Favorite

* id
* user_id
* entity_type
* entity_id
* created_at

Possible entity types:

* destination
* hotel
* property
* place

Prevent duplicate favorites.

Use a unique constraint such as:

user_id + entity_type + entity_id

---

# 12. FAVORITE API

Potential endpoints:

GET /api/v1/favorites

POST /api/v1/favorites

DELETE /api/v1/favorites/:id

or:

PUT /api/v1/favorites/:entityType/:entityId

DELETE /api/v1/favorites/:entityType/:entityId

Follow the project's existing API style.

---

# 13. FAVORITE UX

Favorite button should:

* Show active state
* Show inactive state
* Prevent duplicate requests
* Handle network errors
* Revert safely if server update fails

Do not falsely show a successful favorite when the server rejected the request.

---

# 14. FAVORITES SCREEN

Create/complete:

Profile
→ Favorites

Display tabs or filters:

* Destinations
* Hotels
* Properties
* Places

Only show categories that contain data.

Empty state:

"No favorites yet"

Provide:

"Explore"

---

# 15. MIGRATION FROM LOCAL FAVORITES

Inspect the existing AsyncStorage favorite implementation.

Do not blindly delete existing local favorites.

If practical:

On first authenticated sync:

1. Read existing local favorites.
2. Send valid favorites to server.
3. Merge with existing server favorites.
4. Remove duplicates.
5. Clear obsolete local-only state.

If migration is risky, document the chosen approach.

The server must become authoritative afterward.

# PART C — REVIEWS & RATINGS

## 16. REVIEWS

Implement reviews for eligible completed experiences.

Initially support:

* Hotels
* Destinations where appropriate

The architecture should allow future reviews for:

* Places
* Land/property experiences

---

# 17. REVIEW ELIGIBILITY

For hotel reviews:

Only users with a valid completed/eligible booking should be allowed to submit a review.

Do NOT allow arbitrary users to create hotel reviews.

Server must verify:

* User identity
* Booking ownership
* Hotel relationship
* Booking status
* Review eligibility

---

# 18. RATING

Use a 1–5 star rating.

Require:

* Rating between 1 and 5

Optionally support:

* Title
* Comment

Validate comment length.

Do not accept:

* HTML injection
* Script content
* Excessively large payloads

---

# 19. REVIEW MODEL

Possible:

### Review

* id
* user_id
* entity_type
* entity_id
* booking_id where applicable
* rating
* title
* comment
* status
* created_at
* updated_at

Status can support:

* pending
* published
* rejected

If moderation is not yet required, keep the simplest safe workflow.

---

# 20. REVIEW API

Potential endpoints:

GET /api/v1/reviews

POST /api/v1/reviews

PUT /api/v1/reviews/:id

DELETE /api/v1/reviews/:id

Use entity-specific filtering where appropriate.

Example:

GET /api/v1/hotels/:hotelId/reviews

# 21. REVIEW DISPLAY

* Average rating

* Recent reviews

* Rating
* Comment

# 32. SECURITY

Strictly enforce:

Users can only:

* View their notifications
* Mark their notifications read
* View their favorites
* Modify their favorites
* Create their eligible reviews
* Modify their own reviews

Users cannot:

* Create notifications
* Change notification ownership
* Favorite on behalf of another user
* Create reviews for another user
* Change review status
* Modify another user's review

All authorization must be server-side.

* review status
