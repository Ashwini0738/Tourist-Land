## 1. Harden payment.captured validation

Review the Razorpay webhook/event processing, especially the code that handles:

`payment.captured`

Do not mark a booking/payment as successfully paid based only on:

- valid webhook signature
- event type = payment.captured
- matching amount
- matching currency

The normalized Razorpay payment object must also satisfy:

- `status === "captured"`
- `captured === true`

If either condition is missing or false:

- do not mark the booking as paid
- do not transition payment state to successful/captured
- safely record/log the event according to the existing architecture
- preserve idempotency
- return the appropriate webhook response without creating an invalid paid state

Do not weaken any existing ownership, amount, currency, idempotency, replay, or checkout-lock protections.

## 2. Verify Razorpay order/payment matching

Review the existing verification flow:

POST /v1/bookings/:reference/payment/verify

Ensure that a payment can only be accepted when all existing required checks pass, including:

- authenticated user owns the booking
- booking/payment belongs to the expected Razorpay order
- amount matches exactly
- currency matches
- payment is actually captured
- Razorpay payment status is valid
- signature is valid
- payment has not already been consumed/replayed
- booking state allows payment
- existing idempotency protections remain intact

Do not remove or weaken any existing security check.

## 3. Fix mobile payment error messaging

Review the Expo mobile Razorpay checkout flow.

Currently, make sure the app distinguishes between these situations:

### A. User cancelled payment
Show a clear cancellation message.

Example meaning:

"Payment was cancelled."

### B. Razorpay/provider explicitly reports payment failure
Show a payment failure message.

Example meaning:

"Payment failed. Please try again."

### C. Razorpay checkout appears to have completed, but the app cannot complete server verification because of:
- network failure
- API timeout
- app interruption
- temporary server communication problem
- unknown verification response

DO NOT tell the user:

"Nothing was charged."

because payment status may be uncertain.

Instead show a safe message such as:

"Payment status could not be confirmed. Please check My Bookings before trying again."

The wording can follow the existing app design, but it must clearly distinguish "failed" from "status unknown".

Do not automatically encourage the user to pay again when payment status is unknown, because this could create duplicate-payment risk.

## 4. Expo Go protection

Razorpay uses a native module and cannot perform real native Razorpay checkout inside standard Expo Go.

Review the current mobile payment code.

Before attempting to load/use the native Razorpay module, explicitly detect whether the required native module is available.

If running in Expo Go:

- do not attempt native checkout
- show a clear message that Razorpay checkout requires the Travel & Land development/preview build
- do not crash
- do not create a booking payment state that implies payment was attempted successfully

Preserve lazy loading of the Razorpay native module.

Do not break normal app startup in Expo Go.

## 5. Preserve dual payment recovery

The application must continue supporting both:

1. Mobile-side payment verification
2. Razorpay webhook recovery

The webhook remains important if:

- app closes after payment
- network fails after payment
- mobile verification request fails
- user leaves the app
- device loses connectivity

Do not remove webhook processing just because mobile verification exists.
